# Experiment Flow Design Notes

**Date:** 2026-09-24  
**Status:** Design note; no implementation changes are authorized by this note alone.

## Scope

This note records five related changes discussed for the formal experiment. The tutorial remains separate from the formal trial count and must not be inserted into the formal task manifest.

The current Run12 package contains **23 unique formal scenes**. The planned experiment will present **25 formal trials** because two scenes are repeated. The implementation must derive trial-count-dependent values from the compiled schedule rather than hard-code either number.

## 1. Trial Progress

Formal trials should show a stable progress indicator:

```text
Trial 1 / 25
```

Requirements:

- Count formal trials only.
- Do not count the four reference-board pages, the interactive tutorial, or the tutorial-complete page.
- Use a one-based `trial_index` for participants.
- Use the total formal count from the resolved experiment schedule.
- Keep the same values in the result data: `trial_index`, `trial_total`, and `task_id`.
- The tutorial may show `Tutorial` instead of a formal trial number.

## 2. Scientific Trial-Order Counterbalancing

The order must not be generated by an uncontrolled browser-side shuffle. It should be generated during compilation and selected deterministically for each participant.

### Recommended method

Use a Williams balanced first-order counterbalancing design. This method is intended to balance immediate sequential/carry-over effects between conditions.

- For an even number `n` of conditions, use `n` sequences.
- For an odd number `n`, a single Latin square cannot fully balance immediate sequential effects; use paired squares, producing `2n` sequences.
- For Run12, `n = 23`, so the recommended sequence count is **46**.
- If a future package has six formal trials, it will use six sequences; participant 7 maps back to sequence 1.
- If a future package has 23 formal trials, participant 47 maps back to sequence 1.

The participant-to-sequence mapping is:

```text
sequence_id = ((participant_number - 1) % sequence_count) + 1
```

The compiled schedule should be explicit and auditable:

```json
{
  "strategy": "williams_balanced_first_order",
  "unique_trial_count": 23,
  "presentation_count": 25,
  "sequence_count": 46,
  "sequences": [
    {
      "sequence_id": 1,
      "task_ids": ["scene_...", "scene_..."]
    }
  ]
}
```

Every result must preserve:

- `participant_number`
- `sequence_id`
- `trial_index`
- `trial_total`
- `task_id`

### Important design boundary

If the experiment is intended to balance furniture type, difficulty, or another experimental condition rather than each unique scene, the square should be generated over those conditions and then mapped to stimuli. That choice must be made before compilation. Treating all 23 unique scenes as conditions is the conservative current interpretation.

### Academic basis

- Williams, E. J. (1949), *Experimental Designs Balanced for the Estimation of Residual Effects of Treatments*.
- Bradley, J. V. (1958), *Complete Counterbalancing of Immediate Sequential Effects in a Latin Square Design*.
- Sharma, V. K. (1975), *An Easy Method of Constructing Latin Square Designs Balanced for the Immediate Residual and Other Order Effects*.

References:

- [Williams, 1949](https://scispace.com/papers/experimental-designs-balanced-for-the-estimation-of-residual-pnfecq8a6w)
- [Bradley, 1958](https://www.tandfonline.com/doi/abs/10.1080/01621459.1958.10501456)
- [Sharma, 1975](https://onlinelibrary.wiley.com/doi/10.2307/3315104)

## 3. Separate Position and Rotation Uncertainty

Each editable furniture group must collect two independent confidence ratings:

```text
How uncertain are you about this object's position?
How uncertain are you about this object's rotation?
```

The user must select and save both before leaving the current furniture group or submitting the trial.

Recommended result shape:

```json
{
  "group_id": {
    "position": 3,
    "rotation": 5
  }
}
```

The words `position` and `rotation` should be visually emphasized with bold weight and a distinct color. The two questions must remain semantically separate in the data and UI.

### Scale direction

Use the following visual order:

```text
5  Very sure
4  Sure
3  Neutral
2  Unsure
1  Very unsure
```

The numeric meaning remains unchanged: 1 is low confidence and 5 is high confidence. Placing 5 at the top and 1 at the bottom is the recommended visual arrangement because the vertical direction communicates higher confidence upward.

## 4. DataPipe as the Production Default

The production compile output should use DataPipe rather than `copy` as its normal save path.

Requirements:

- Production output defaults to `data_save.mode = "datapipe"`.
- Task-level DataPipe saves the completed trial backup.
- Experiment-level DataPipe saves the final complete export.
- The task-level and experiment-level endpoints must be configured independently but use the same participant/session identifiers.
- The actual VPS/DataPipe domain, experiment ID, and optional submit token must come from the confirmed deployment configuration; they must not be invented or copied from a test endpoint.
- `copy` remains available only as a recovery path when automatic saving fails.
- The normal formal result remains plain, readable CSV where the export contract requires CSV.
- The compact trial backup may continue using the existing compressed encoded string inside a self-describing JSON envelope; compression is not encryption.

## 5. Upload Waiting, Retry, and Complete ZIP Recovery

### Per-trial behavior

```text
Complete current trial
-> Show a Saving... overlay
-> Upload trial backup
-> On success, record success and enter the next trial
-> On timeout/failure, record the failure and continue to the next trial
```

The timeout must not erase the completed result or block the participant indefinitely. The result should record:

```text
upload_status = success | failed | timeout
upload_attempts
upload_error
uploaded_at
```

The client may continue retrying in the background with bounded attempts/backoff, but retries must be idempotent or carry a stable backup identifier so they cannot create ambiguous duplicates.

### Final behavior

At the end of the experiment:

1. Upload the complete final CSV export.
2. Retry any failed trial backups.
3. Record the final state of every upload attempt.
4. If automatic upload still has failures, generate one complete ZIP from the authoritative in-memory result set.
5. Show a final recovery page requesting that the participant send the ZIP to the configured research email address.

The ZIP must be complete, not assembled by copying only whichever files failed. It should contain, as applicable:

```text
session.csv
results.csv
raw_results.csv
events.csv
debug.json
tutorial_result.json
trial_backups/
manifest.json
```

The recovery manifest must include identifiers matching the DataPipe submissions:

```text
participant_number
participant_id
session_id
experiment_id
sequence_id
upload_status
failed_filename
failure_reason
timestamp
```

Success and failure are statuses on the same data model, not separate incompatible output formats.

## 6. Repeated Formal Stimuli and Response-Consistency Metadata

The two repeated scenes are formal trials, not hidden checks. The final experiment therefore saves **25 formal trial records**:

```text
23 unique scenes + 2 repeated presentations = 25 formal presentations
```

The repeated presentations and their complete answers must remain in the ordinary formal export and in the recovery ZIP. They are used later to calculate response consistency, but response consistency is not an automatic exclusion rule.

The repeated source images are:

```text
scene_8902bfd7b7e4:
E:/260917/assets/images/stimulus/8902bfd7b7e4_perspective_stimulus_1920x1080.png

scene_15d8ce4dbde3:
E:/260917/assets/images/stimulus/15d8ce4dbde3_perspective_stimulus_1920x1080.png
```

The formal experiment must use these unlabelled source images. It must not use the review images containing `P01`-`P06` labels.

Each presentation should preserve the following metadata:

```text
task_id
presentation_id
repeat_group_id
repeat_index
repeat_of_task_id
trial_index
trial_total = 25
sequence_id
participant_number
```

For a first presentation, use `repeat_index = 1`. For its repeated presentation, use `repeat_index = 2` and the same `repeat_group_id`. The `presentation_id` must still be unique so the two saved answers cannot overwrite one another.

The complete answer for both presentations includes final object state, position uncertainty, rotation uncertainty, interaction events, timing, and upload status. This allows later calculation of:

```text
repeat_position_difference
repeat_rotation_difference
repeat_position_confidence_difference
repeat_rotation_confidence_difference
response_consistency_index
```

No `Process Integrity Index` is required in the application or export. The application should preserve raw metadata only; derived participant-quality indices can be calculated offline by the researcher.

### Repeat spacing

There is no universal academic rule that a repeated stimulus must be exactly seven trials apart. The literature supports treating lag as a design variable because short lags can increase memory, practice, and carry-over effects; the appropriate interval depends on the task and study purpose. The seven-trial rule should therefore be documented as a preregistered design constraint, not described as a universal law.

The recommended constraint is **at least seven intervening formal trials** between the two presentations of the same scene. With one-based trial positions, this means:

```text
abs(position_2 - position_1) >= 8
```

The schedule generator must also ensure the two repeated groups are not adjacent. It should generate candidate 25-presentation schedules, reject schedules that violate the constraints, and emit diagnostics showing the achieved lag for each repeated group.

This is a study-specific preregistered constraint, not a universal seven-trial standard. The rationale is consistent with test-retest methodology, which treats the interval as dependent on the purpose and context of the measurement, and with work showing that response behavior can depend on the lag between repeated stimuli:

- [Test-retest reliability and interval choice](https://pmc.ncbi.nlm.nih.gov/articles/PMC5466566/)
- [Retest effects in working-memory tests](https://pubmed.ncbi.nlm.nih.gov/29907925/)
- [Sequential learning and lag effects](https://pubmed.ncbi.nlm.nih.gov/20396653/)

The base counterbalancing design remains based on the 23 unique scenes. The two repeat presentations are inserted into each candidate sequence under the spacing constraints, after which the complete 25-presentation schedule is validated.

### Analysis boundary

Both repeated answers are valid formal data. `response_consistency_index` is a soft diagnostic and sensitivity-analysis variable only. It must not be used alone to exclude a participant, alter scoring, or remove either repeated row from the primary export.

## Related Package Validation Issue

The current validator reports:

```text
Tutorial task scene_edc634ac7856 is missing from manifest
```

This is caused by the validator checking `config.tutorial.taskId` against the formal package manifest loaded from `config.baseUrl`. The tutorial task is intentionally in the separate tutorial package at `config.tutorial.baseUrl`.

Correct validation behavior:

1. Load the formal manifest from `config.baseUrl`.
2. Validate all formal trials against that manifest.
3. Load the tutorial manifest from `config.tutorial.baseUrl`.
4. Validate the tutorial task against the tutorial manifest.
5. Never add the tutorial task to the formal task manifest or the 23-scene source manifest; the 25-presentation order belongs in the compiled schedule.

The validator also contains an older assumption that formal trials must always use `preview_then_reconstruct`. That rule must be selected by the package/reference condition rather than applied unconditionally, because persistent reference mode and current direct-reconstruction packages are valid configurations.
