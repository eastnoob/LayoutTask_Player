# Layout Task Protocol Kit

The protocol kit defines the files external generators should produce and the files the player compiler consumes.

Canonical input is standard JSON, not JSON5. CSV/Excel may be added later as import adapters.

Main files:

- `schemas/layouttask.batch.schema.json`: language-neutral structural preflight schema.
- `examples/minimal-batch.json`: smallest working batch fixture.
- `examples/scoring-example.json`: batch fixture with canonical relative targets.
- `examples/full-preview-collision/batch.json`: complete preview stimulus plus collision reconstruction fixture.
- `rhino.md`: Rhino-facing field dictionary and conventions.
- `player-ingestion.md`: Player-side validation, compilation, runtime loading, result, and scoring workflow.
- `compile-workflow.md`: recommended assemble/validate/compile/serve workflow and default flags.
- `relative-target-coordinate-semantics.md`: compact report for object pose coordinates, relative answers, and optional absolute analysis data.
- `templates/`: fill-in templates and export checklist.

Important state rule: in batch objects, `x`, `y`, and `rotation` define the reconstruction initial pose shown to the participant. For variable objects, the canonical correct answer is `target.relative`: signed movement and rotation steps from that initial pose. `target.absolute` is optional derived/analysis data and is not required in authored source packages.

Unit rule: `world.unit` labels the task-space unit for coordinates, dimensions, grid size, movement step, collision geometry, and optional `target.absolute` values. `target.relative` and saved relative answers are step counts, not world-unit distances. Asset `intrinsic_unit` labels only the source SVG/image's internal coordinate system. Local unit override fields are reserved and not implemented in v1.

Coordinate rule: object `x/y` is the object's anchor pose in the room/world coordinate system. For `anchor: "center"`, this should normally be the object's Rhino/CAD bbox center after projection into the same 2D coordinate system used by `world.viewBox` and the background SVG. SVG `viewBox` is asset-local and does not define object room position.

SVG sizing rule: for 1:1 SVG/CAD/Rhino exports, object asset dimensions and background placement may be omitted. The Player then reads the SVG root `viewBox`; object SVGs use `viewBox.width/height`, and background SVGs use `viewBox.x/y/width/height`. Explicit JSON values still override viewBox inference. Raster assets still need explicit dimensions.

For Rhino/CAD exports, do not omit explicit dimensions unless the exported SVG
`viewBox` is already in the same task-space world units as `world.viewBox`.
The common Rhino pipeline should preserve `background.x/y/width/height` and
object `default_width/default_height` from bbox data. Collider SVG sidecars can
share the visual SVG's local viewBox, but attaching colliders does not require
trusting SVG viewBox for display size.

Object collider rule: visual furniture SVGs are not automatically treated as solid collision geometry. `box` remains the legacy fallback. For precise object-object collision, provide collider SVGs under `assets/collision/objects/`, usually named like `chair_a_COLLISION.svg`, and reference them with `collision.shape: "asset_outline"`. At runtime, `asset_outline` is fetched once and resolved to object-local `polygons`. Collider SVGs should share the visual SVG's local coordinate system and contain filled `rect`, positioned `<use>` rectangles, `polygon`, or closed `path` geometry; curves in paths are flattened. Affine `matrix`, `translate`, `scale`, and `rotate` transforms are applied. Raster `<image>` nodes are ignored. The parser rejects masks, clip paths, filters, and rounded rects.

Rhino adaptor rule: `pixi run assemble-stimuli-csv --attach-collider-svg`
attaches same-name object collider SVGs and enables task-level discrete
collision. If a paired `*_group` / `*_variable` SVG export shares one viewBox
axis but Rhino bbox dimensions disagree on that same axis, add
`--normalize-paired-svg-dimensions --asset-root <package-root>` after copying
assets into the package; the adaptor will use the group SVG-to-world scale for
the variable asset instead of hand-editing `objects.json`.

Runtime player files can be generated by `compile-batch`; authors should not hand-maintain generated task files for large batches.

For day-to-day Rhino/StimuliGenerator exports, follow `compile-workflow.md`.
It records the recommended default flags, package layout, local URL shape, and
diagnostic checks.

Use the JSON Schema for generator-side structural checks. Use `pixi run validate-batch` as the canonical semantic validator before compiling; it also catches cross-record rules such as duplicate `task_id` values and duplicate object IDs within a trial.

`compile-batch` writes JSON runtime files and scoring references. A deployable alternate `base` directory must also contain the referenced asset files and the Player UI icons under `assets/icons/`.

The files under `protocol/examples/assets/` are self-authored fixtures for protocol and visual testing, including local asset libraries. They are intentionally simple and do not come from Rhino. Use them to verify the compiler/player/scoring chain before testing real Rhino exports.
